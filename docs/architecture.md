# ぬまコン 設計と決定事項

このファイルは、ぬまコンの構成・方針・担当をまとめたものです。

## 概要

- 北海道沼田町向けの Web アプリ
- 町民が自然な日本語で質問すると、町の行政資料（PDF）をもとに、出典付きで答えるチャット（RAG）
- あわせて、回覧板の表示と、職員向けの管理画面（資料・回覧板の登録）を持つ
- 当面のゴール: テキストのチャットと管理画面を、製品として見せられるところまで作る（プロトタイプ）。音声入力は後回し
- 締め切り: 2026年12月23日

## 方針

- バックエンドは Rust（Axum）
- PDF の解析は docling-serve を Docker で立て、HTTP で呼ぶ（md と JSON を取得。JSON はページ番号などの位置情報に使う）
- 認証はリバースプロキシの Caddy が行う。職員用の URL に Basic 認証をかけ、ログインした職員名を `X-Remote-User` ヘッダーで backend に渡す。外から送られてきた `X-Remote-User` は Caddy が消す
- チャットの応答は SSE で少しずつ返し、出典は最後に送る
- データの正本は SQLite。Qdrant は SQLite からいつでも作り直せる控えとして扱う
- ベクトル化と回答の生成は Ollama で行う
- RAGはなるべく自分たちで作成する
- 動かすのはサーバー1台、Docker Compose。
- 音声入力は後で追加する（「今後の予定」を参照）

## 構成

コンテナは5つで、すべて横並び（どれも他のコンテナの中には入らない）。リポジトリ直下の `compose.yaml` 1つで管理する。

| コンテナ | 役目 | 用意するもの |
| --- | --- | --- |
| caddy | 入口。HTTPS、職員用 URL のログイン、`X-Remote-User` の付与と除去、`front/` の HTML の配信 | 公式イメージ＋Caddyfile |
| backend | 自分たちの Rust のサーバー。中に api と ingest の2つのクレートがあるが、ビルドすると1つのプログラム | `back/` からビルド |
| qdrant | ベクトルの保存と検索 | 公式イメージ |
| ollama | ベクトル化と回答の生成 | 公式イメージ |
| docling-serve | PDF を md と JSON に変換 | 公式イメージ |

- 外に公開するポートは caddy の 80/443 だけ。ほかのコンテナには外から届かない
- コンテナ同士はサービス名で呼び合う（例: backend から `http://ollama:11434`）
- フロントエンドは自分のコンテナを持たない。ただの HTML・JS・CSS なので、Caddy にフォルダを見せて配ってもらう

### 保存先（名前付きボリューム、候補）

ボリュームの分け方と名前は候補。

| ボリューム | 中身 |
| --- | --- |
| caddy_data | HTTPS の証明書（消すと証明書を取り直すことになるので必須） |
| caddy_config | Caddy の設定の保存 |
| app_data | SQLite と、アップロードされた元の PDF |
| qdrant_data | Qdrant のデータ |
| ollama_models | Ollama のモデル |

`docker compose down -v` は名前付きボリュームも消すので使わないこと。

## ディレクトリ構成

決まっているのは、リポジトリ直下に `compose.yaml` を置き、フロントとバックエンドを別のフォルダに分けることだけ。フォルダ名（`front/`・`back/`）は候補で、下の図もイメージを示す例。

```
numacon/
├── compose.yaml
├── Caddyfile
├── .env.example
├── back/
│   ├── Cargo.toml        # workspace
│   ├── Dockerfile
│   ├── migrations/
│   └── crates/
│       ├── api/
│       └── ingest/
├── front/
│   ├── index.html
│   ├── admin.html
│   └── static/
├── scripts/
└── eval/
```

- フォルダは「何として動くか」で分け、「誰が書くか」は担当で決める
- フロントのコードは `caddy/` に入れない。設定ファイルを誤って配信する事故を防ぐため、また持ち主が違うため
- `.env` は Git に入れない。値を空にした `.env.example` を置く

例の中のフォルダの役目:

- `scripts/`: 運用のための小さなスクリプト。Ollama のモデルを取ってくる、SQLite と元の PDF をバックアップ・復元する、など（インフラ担当）
- `eval/`: 精度評価に使うもの。想定質問の一覧（質問ごとに正解の資料・ページ・答え、答えが無い質問は「該当なし」）、評価の結果の記録、あとで評価を自動で回す道具（精度評価担当）

| 場所 | 担当 |
| --- | --- |
| `back/` のうち API・データベースの部分 | バックエンド班 |
| `back/` のうちデータ処理（PDF の変換、チャンク、Qdrant）の部分 | データ処理班 |
| `front/` | フロントエンド班 |
| `compose.yaml`、`Caddyfile` | インフラ担当 |

## データの流れ

### 町民が質問したとき

1. ブラウザが `POST /api/chat` で質問を送る
2. Caddy が backend に渡す
3. api が ingest の検索を呼ぶ。質問を Ollama でベクトルにし、Qdrant で意味の近いチャンクを探す
4. 近いものが見つからなければ「該当なし」を返して終わる
5. 見つかれば、それをもとに Ollama で回答を作り、SSE で少しずつ返す
6. 最後に出典（資料名・ページ）を送る

### 職員が資料を登録したとき

1. 職員が管理画面から資料を送る。Caddy がログインを確かめ、職員名を付けて渡す
2. api が PDF を保存し、状態を「処理待ち」にしてすぐ返す
3. 裏で ingest が動き、docling-serve で変換してチャンクに分ける
4. チャンクを SQLite に保存する
5. ingest がチャンクをベクトルにして Qdrant に登録する
6. 状態を「完了」にする。管理画面は数秒ごとに一覧を取り直して状態を表示する

## データ処理班とバックエンド班の受け渡し

ingest は backend から関数として呼ばれるライブラリ。同じ Cargo workspace に入れて型を共有する。受け渡しの具体的な形（チャンクの項目、関数の分け方）は未決で、2つの班で合意したらここに書く。

形が決まる前から守ること:

- 登録と検索で、必ず同じ埋め込みモデル・同じ関数を使う
- 失敗したらエラーを返し、プロセスを落とさない

### Qdrant のコレクション（案）

- 名前にモデル名を入れる（例: `chunks_bge_m3`）。モデルを変えたら新しいコレクションを作る
- bge-m3 は 1024 次元、距離は Cosine
- payload: `document_id`（索引を付ける）、`page`、`heading`、`text`

### チャンク分割の方針（案。精度評価の結果を見てデータ処理班が決める）

- 見出しで区切る
- 長すぎたら（目安 400〜800 字）「。」や段落の切れ目で分け、前後を1〜2文重ねる
- 表は割らない。大きすぎる表は行ごとに分け、各チャンクに見出し行を付け直す
- 見出しを本文の頭に付けてからベクトルにする
- ヘッダー、フッター、ページ番号、目次は捨てる
- 短すぎるものは次のかたまりとまとめる

## SQLite に保存するもの

| テーブル | 主な列 | 時期 |
| --- | --- | --- |
| documents | id, title, category, content, file_path, schedule, publish, status, error_message, created_at | プロトタイプ |
| chunks | id, document_id, seq, text, page, heading, embedding_model | プロトタイプ |
| notices | id, type, title, body, photo, created_at, updated_at | 回覧板 API を作るとき |
| audit_logs | id, user, action, target, created_at | 操作ログを作るとき |
| chat_logs | 保存範囲と保持期間を決めてから | 未定 |

元の PDF はファイルとして保存し、SQLite には置き場所だけを書く。ベクトルは Qdrant に入れる。テーブルの変更は `sqlx migrate` で管理する。

## モデル

- 埋め込み: Ollama + `bge-m3` で始める。日本語特化の `ruri-v3` も候補（GGUF 版はあるが Ollama で動くか未確認。使う場合は質問に「検索クエリ: 」、チャンクに「検索文書: 」を付ける。ベクトルの次元も変わる）
- ベクトルの次元はコードに決め打ちせず、使うモデルに合わせる
- 回答用: VRAM 8GB に収まる 7〜8B の 4bit 量子化を前提にする。候補は LLM-jp-4 8B instruct（`mmnga-o/llm-jp-4-8b-instruct-gguf` の Q4_K_M）など。考える過程を出力する thinking 系は最初の文字が遅いので、チャットには instruct 系が向く。精度評価で2〜3個比べて決める
- 形態素解析は当面使わない。固有名詞や数字の質問で検索が外れるようなら、キーワード検索の併用を検討する

## Caddy

- 職員用の URL: `/admin`、`/admin/*`、`/api/admin/*`。職員用の機能は必ずこの下に置く
- `/api/*` は backend へ、それ以外は `front/` のファイルを返す（`/admin` は `admin.html` に読み替える）
- 資料のアップロードは 20MB まで（backend 側の上限もそろえる）
- 秘密の値（職員のユーザー名、パスワードのハッシュ、ドメイン名）は `.env` から環境変数で読む
- 開発中は `localhost` で動かす。SSE と `X-Forwarded-For` の扱いは Caddy の既定で問題ない

## 班ごとのタスク

### バックエンド班

- プロトタイプに必須
    - データ処理班と受け渡しの形を合意する
    - Ollama に接続する
    - SQLite のテーブル設計とマイグレーション
    - `POST /api/chat` の中身（検索 → 該当なし判定 → 回答生成）。SSE で送る形はできている
    - 資料の登録・一覧を SQLite に保存するよう作り変える、ファイルの中身を保存する（今はメモリに置いていて、ファイルは名前だけ）
    - 資料の登録後の非同期ジョブ、処理状態の記録
    - 資料の削除（SQLite と Qdrant の両方から）
    - 入力長の制限、アップロードの上限（Axum の `DefaultBodyLimit` を 20MB に）、タイムアウト
    - 設定を環境変数から読む
- 製品として見せる前
    - 元の PDF の配信
    - 回覧板の API
    - `X-Remote-User` を読んで操作ログを残す
    - Docker 化とヘルスチェック
    - エラーレスポンスの形の統一
- 公開前
    - レート制限（`X-Forwarded-For` で相手を見分ける）
    - 構造化ログ（`tracing`。最初から入れておくと書き直さずに済む）
    - チャットログの保存範囲と保持期間を決める

### データ処理班

- プロトタイプに必須
    - バックエンド班と受け渡しの形を合意する
    - docling-serve を呼んで PDF を md と JSON にする
    - チャンク分割と、ページ番号・見出しの付与
    - Ollama でのベクトル化
    - Qdrant のコレクション設計と、登録・検索・削除
    - 実際の行政 PDF で変換結果を目で確かめる
    - 失敗したらエラーを返す（落ちない）
    - テキストだけの資料（管理画面のフォームで登録できるため）
- できたら
    - 読めない PDF の種類分けと、管理画面向けの理由の文言
- 本番前
    - Qdrant を作り直す手順の確認
    - 精度評価の結果を見て、チャンク分割を調整する

docling-serve の版によっては、分割の機能（HybridChunker）を HTTP から呼べる。使えるなら区切りの基本部分を自分で書かずに済む。

### フロントエンド班

チャットの SSE 受信、出典（クリックで元の PDF を開く）・該当なし・エラーの表示、回答待ちの表示、免責文は作成済み。

- プロトタイプに必須
    - `done` が来ないまま接続が切れたとき、回答が途中で切れたと表示する（今は接続が切れたことで終わりと判断しているため、途中で切れても気づけない）
    - チャットの入力欄に `maxlength` を付ける（数字は backend の上限に合わせる）
    - 資料の登録を `FormData` で API に送る（`Content-Type` は自分で付けない）
    - 資料の一覧と削除を API につなぎ変える（削除の確認はそのまま使う）
    - 資料の一覧に処理状態（処理待ち・処理中・完了・失敗と理由）を出し、数秒ごとに更新する
    - Flask の残りのファイル（`app.py`、`requirements.txt`、`Dockerfile`）を消す
    - backend ができたら、本物の API につないで確かめる
- できたら
    - backend のエラーの形が決まったら、管理画面でエラーの理由を表示する（今は状態番号しか出ない）
    - 回覧板を API まで作る（バックエンド班と相談）
- 本番前
    - 長い間応答が無いときの表示

### インフラ担当

- プロトタイプに必須
    - Ollama のモデルを取ってくるスクリプト
    - Caddyfile を書いて `localhost` で確かめる（backend の代わりに `traefik/whoami` を置くと、届いたヘッダーを確認できる）
- できたら
    - backend の Rust 用 Dockerfile
    - `healthcheck` と `restart` の設定
    - コンテナごとのメモリ上限（docling が重い PDF でほかを巻き込まないように）
    - ログの最大サイズの設定
    - `.gitattributes` で `*.sh` の改行を LF に固定する
    - README に起動手順を書く
- 本番前
    - バックアップと復元のスクリプト（SQLite と元の PDF。Qdrant は作り直せるので不要）と、実際に戻せるかの確認
    - 本番サーバーに必要なメモリと VRAM を、`docker stats` と `nvidia-smi` で測っておく

### 精度評価（案）

- 町民の口語で想定質問を 50〜100 件作る。答えが資料に無い質問も1〜2割混ぜる
- 質問ごとに、正解の資料・ページ・答えを書いておく
- 結果の返し先
    - 検索で正しいチャンクが出ない → データ処理班（区切り方）
    - 検索は合っているのに回答がおかしい → バックエンド班（プロンプト）
    - 資料に無いのに答える、またはあるのに「該当なし」になる → バックエンド班（しきい値）
- 直したら同じ質問でもう一度評価する

## 開発・テスト環境

- チームで共有するテスト環境: GPU のある PC で compose を立て、Tailscale でメンバーがつなぐ。ルーターのポートを開けて公開はしない
- ドメイン: 開発中は不要（`localhost` はブラウザに安全な場所として扱われる）。本番は町のドメインのサブドメインが理想
- GitHub Actions: Rust のコードができたら導入する。最初は `cargo fmt --check`、`cargo test`、`docker compose config`。`cargo clippy` は最初は警告だけにする。`main` への取り込みは、必須チェックを通したうえで手動で Merge する

## 今後の予定

- 音声入力: whisper.cpp のサーバーを6つ目のコンテナとして追加し、backend 経由で呼ぶ。モデルは `kotoba-whisper v2.0` の ggml 版（q5_0）が有力。マイクは HTTPS か `localhost` でしか使えない。録音は 30 秒程度に制限する

## まだ決まっていないこと

- ディレクトリ名（`front/`・`back/` は候補）
- 名前付きボリュームの分け方と名前
- データ処理班とバックエンド班の受け渡しの形（チャンクの項目、関数の分け方）
- 資料に画像の添付を許すか（最初は PDF だけにするほうが楽）
    - 受け付けるなら、docling の OCR（日本語の指定が必要）で文字を読み取る。チラシの飾り文字や斜めの写真は読み間違えやすい
    - 読み間違いが検索に入らないよう、読み取った文章を職員が確かめて直せる画面があるとよい
    - スキャンした PDF も中身は画像なので、PDF だけにしても同じ問題は残る。実際の資料にスキャンが多いかを先に確かめる
- 資料の公開日・対象日程の使い道（表示だけか、検索の絞り込みにも使うか）
- 回覧板の写真の送り方と、日付の項目を足すか
- 回答用 LLM と埋め込みモデルの最終決定
